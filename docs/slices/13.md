# Slice 13. Replies that survive a dropped connection

A reply keeps running on the server when the phone drops its connection. Orbit saves the whole reply, and the phone picks the stream back up when it returns. Only the **Stop** button stops a reply. Thinking shows a running timer, and a reply that holds only thinking is saved too.

**Branch** `feat/durable-replies`. **Depends on** nothing. Fixes gap B1 and gap G5 in `docs/design/gap-analysis.md` (on the `docs/gap-analysis` branch).

## Why

The maintainer lost a paid reply on a phone. The prompt went out at 17:13:51 UTC. The model thought for about 110 seconds, the Cloudflare edge closed the stream, and Orbit logged `chat end without text finished unknown step-start,reasoning`. Nothing was saved. The provider still billed the thinking tokens.

Three things in the code cause this:

1. The chat route hands the browser request's abort signal to the model call (`abortSignal: request.signal`, `src/app/api/chat/route.ts:135`) and to the tools (`toolsForTurn(..., request.signal)`, `route.ts:99`). A dropped connection cancels the provider request and any running sandbox or GitHub call.
2. A cut-off reply is saved only when it has text or a tool part. `shouldSaveReply` returns `visible` (`src/lib/messages.ts:101`), `upsertMessage` drops an assistant message without a visible part (`messages.ts:120`), and `assistantHasVisiblePart` ignores reasoning (`src/lib/genui/spec.ts:65-75`). A cut during thinking throws the whole reply away.
3. The client cannot reconnect. `useChatRuntime` in `src/components/chat/chat-panel.tsx:57-65` has no resume option, so the phone shows `network error` and **Retry** (`src/components/chat/messages.tsx:90-109`). Retry runs the turn again and pays for the thinking twice.

Gap G5 makes it worse. The thinking chip reads "Thinking", then "Thought", with no time (`src/components/chat/reasoning.tsx:15`). A long think looks like a stall, so people switch apps, and on iOS a backgrounded page loses its connections (a guess about cause, from the gap analysis).

ChatGPT shows a finished answer in full when you come back to a chat. Orbit runs one process for its users, so an in-memory store of running replies is enough. No Redis is needed.

## Scope

Ships:

- A server-side registry of running replies. A reply runs to the end whether or not a browser is attached.
- `POST /api/chats/[id]/stop`, the only way to stop a reply.
- `GET /api/chats/[id]/stream`, which replays a running reply from its first chunk and then follows it live.
- Client resume through the `resumable` option of `AssistantChatTransport`, plus a resume on `online` and on `visibilitychange` when the page becomes visible.
- A reload or a second tab attaches to a reply that is still running. A send from that tab while the reply runs gets 409 and stores nothing.
- A user can have at most 4 replies running, and ended runs keep at most 64 MB of replay chunks in total.
- A reply that holds only reasoning is saved. A stopped or failed reply carries a small end mark that shows **Stopped** or **Interrupted**.
- Thinking shows `Thinking 12s` while it runs and `Thought for 1m 50s` afterwards, also after reload.
- SSE keep-alive comments every 15 seconds, so a model that thinks without sending anything does not hit Cloudflare's 125-second read timeout.
- `discardReplyRun(chatId)` for slice 16, so deleting a chat can stop its reply and clear its saved stream.
- Delete `export const maxDuration = 120` (`src/app/api/chat/route.ts:20`). It does nothing under `next start`, and a reader takes it for a limit.

Does not ship:

- Surviving a server restart. A reply that is running when the process stops is lost, as today. Saving partial parts during the stream is a later change.
- Continuing a cut reply where it stopped. **Retry** still runs the turn again as a new sibling.
- More than one Orbit process. The registry lives in one process's memory.
- Usage and cost per reply (gap G4).

## Design

### Data shape

The registry holds one run per chat. Its state is a union, so a run cannot be both live and finished.

```ts
// src/lib/reply-runs.ts
import type { UIMessageChunk } from "ai";

type RunState =
  | { kind: "starting" } // reserved before planChatWrite, no stream yet
  | { kind: "running"; listeners: Set<ReadableStreamDefaultController<UIMessageChunk>> }
  | { kind: "stopping"; listeners: Set<ReadableStreamDefaultController<UIMessageChunk>> }
  | { kind: "ended"; endedAt: number };

type ReplyRun = {
  chatId: string;
  userId: string;
  replyId: string; // write.responseId. Also the resumable stream id the client stores.
  controller: AbortController; // the only signal the model and the tools see
  chunks: UIMessageChunk[]; // every chunk since "start", replayed to each new listener
  state: RunState;
  done: Promise<void>; // settles after onEnd has saved the reply and closed the tools
};
```

The map lives on `globalThis`, so `next dev` module reloads find the same runs. An ended run stays for `REPLAY_GRACE_MS = 10 * 60_000`, then a timer with `unref()` deletes it. Ten minutes covers a phone that comes back after a short lock.

Two limits keep the map bounded once slice 18 lets several people in. Both are starting values for the maintainer to confirm.

- `MAX_RUNNING_PER_USER = 4`. A fifth reservation for the same user is refused, and the route answers 429 `Too many replies running.` Closing a tab no longer ends a run, so without a cap one person could start runs in many chats and leave them all going.
- `REPLAY_BUDGET_BYTES = 64 * 1024 * 1024`, shared by every ended run. The pump adds the length of each chunk's JSON to its run's size as it appends it. When an ended run pushes the total past the budget, the oldest ended runs are dropped first. A resume for a dropped run gets 204 and takes the reload path in step 8 of the flow. A running run is never dropped, because its chunks are the only copy of the reply until `onEnd` saves it.

The end mark is a data part appended to the saved parts when the reply was interrupted:

```ts
type ReplyEndPart = { type: "data-reply-end"; data: { reason: "stopped" | "failed" } };
```

Thinking time rides on the reasoning part's `providerMetadata`, under its own key:

```ts
type ReasoningTiming = { orbitTiming: { startedAt: number; thoughtMs?: number } };
```

The key is `orbitTiming`, not `orbit`. The openai-compatible provider is created with `name: "orbit"` (`src/lib/provider.ts:83`), and the AI SDK passes part metadata back as provider options under the same key on the next request. A key named `orbit` would reach the provider (inferred from how `convertToModelMessages` carries `providerMetadata`; turn 1 checks it with a request-log assertion).

### Flow

1. `POST /api/chat` parses the body, then calls `reserveReplyRun(chatId, userId)` before `planChatWrite`. If the chat has a run in `starting` or `running`, it returns 409 "A reply is still running." and writes nothing. If the run is `stopping`, it awaits `run.done` for up to 5 seconds, then reserves. That keeps **Stop** then **Regenerate** working. The reservation checks and sets the map with no `await` in between, so two requests cannot both get it. It has to come first, because `planChatWrite` saves the incoming user message and moves `head_id` (`src/lib/messages.ts:206-209`), and the route then touches the chat and starts the title (`route.ts:69-85`). A 409 after that would leave the rejected message stored. The route also awaits `toolsForTurn`, `recall`, and `convertToModelMessages` before it has a stream, so a check placed after planning would let two requests through. When planning fails, or anything throws before `startReplyRun`, the route calls `releaseReplyRun(run)`, which removes a run still in `starting`. Planning then goes on as today (`route.ts:54-93`).
2. The route creates the run's `AbortController` first. It passes `controller.signal` to `toolsForTurn` and to `streamText` as `abortSignal`. `request.signal` reaches neither.
3. `result.stream` goes through `stampReasoningTimes()` before `toUIMessageStream`. That transform adds `orbitTiming.startedAt` to each `reasoning-start` and `startedAt` plus `thoughtMs` to each `reasoning-end`. It keeps the provider's own keys. `reasoning-end` replaces the part's metadata (`node_modules/ai/dist/index.js:6738`), so the end chunk must carry both fields. Stamping before `toUIMessageStream` means the saved message in `onEnd` and the live client get the same parts.
4. `startReplyRun(run, stream)` moves the reserved run to `running`, takes the UI stream, and starts a pump. The pump reads every chunk, appends it to `chunks`, and enqueues it to each listener. Nothing a browser does can cancel the pump. `onEnd` (`route.ts:147-177`) still saves the reply through `upsertMessage`, and it now runs because the pump reads to the end.
5. The POST response is `createUIMessageStreamResponse({ stream: watchReply(run), keepAliveMs: 15_000, headers: { "x-resumable-stream-id": run.replyId } })`. `watchReply` returns a new stream that replays `chunks` and then follows the run. Cancelling it removes only that listener.
6. A dropped connection ends that response. The model keeps going and the pump keeps reading.
7. The client keeps the stream id in `sessionStorage` under `orbit-stream:<chatId>`. On mount, on `online`, and on `visibilitychange` to visible, it resumes when an id is pending and the thread is not running. The resume calls `GET /api/chats/[id]/stream`. That route replays from the first chunk, so the AI SDK rebuilds the message with its original `messageId`. The default `resumeStreamIsReplay` is `true` (`node_modules/ai/dist/index.d.ts:6549-6555`), which matches.
8. When the run is gone (more than 10 minutes after its end, or never), the stream route returns 204. assistant-ui clears the stored id on 204 or 404 (`node_modules/@assistant-ui/ai-sdk/src/transport/AssistantChatTransport.ts:152-158`). If the screen still shows a partial reply, the panel reloads the page so the saved copy loads.
9. **Stop** calls `POST /api/chats/[id]/stop`, then cancels the local run. The route moves the run to `stopping` and aborts its controller. `onEnd` sees `isAborted`, keeps any stopped code-run output through `stopped.apply` as today, and saves.
10. On save, `onEnd` appends `data-reply-end` with `reason: "stopped"` when `isAborted`, or `reason: "failed"` when the outcome is not `completed`. A completed reply gets no end mark.
11. The chat page (`src/app/(app)/c/[id]/page.tsx`) asks `findReplyRun(chatId, userId)`. If a run is `running`, it passes `liveReplyId` to `ChatPanel`, which writes it to the resumable storage before the runtime mounts. A reload, or the same chat in a new tab, attaches to the running reply.

The client needs its own listeners. assistant-ui builds its chat with `useChat({ chat })` and no `resume` option (`node_modules/@assistant-ui/ai-sdk/src/runtime/useChatThread.ts:299-302`). The AI SDK resumes on `visibilitychange` only for `useChat({ resume: true })` (`node_modules/@ai-sdk/react/dist/index.js:228-256`). assistant-ui resumes once on mount when a stream id is pending (`useChatThread.ts:484-505`). Pass `canResume: true` to `useChatRuntime` so a failed reconnect keeps the id and `runtime.thread.resumeRun` can try again (`useChatThread.ts:50-55`, `useAISDKRuntime.ts:149-155`).

### What is saved

`assistantHasVisiblePart` counts a reasoning part with non-empty text, as well as text and tool parts. Nothing else changes about saving. A stop before any text or reasoning arrives still leaves the head on the saved prompt. `persistIncoming` (`messages.ts:162-163`) uses the same function, so a reasoning-only reply stays on the path the next turn sends.

The rule "Nothing is saved without text" in `ARCHITECTURE.md` becomes "Nothing is saved that you did not see". Reasoning that streamed counts as seen. In `docs/architecture/ChatTurn.tla`, `TextArrives` now means text or reasoning arrives. A dropped connection is not a transition in that model any more, because it no longer changes the server's phase. Rerun TLC and rebuild the chart.

### UI

- **Thinking chip.** `Reasoning` reads `providerMetadata.orbitTiming`. While running, it shows `Thinking 12s` and ticks once a second from `startedAt`, clamped at zero, so a resumed replay shows the real elapsed time. When done, it shows `Thought for 12s` or `Thought for 1m 50s`. A part saved before this slice has no timing and keeps the word `Thought`. Seconds use tabular figures. The label is a pure function, `thoughtLabel(ms)`, in `src/lib/thought-time.ts`.
- **Reconnecting.** While a resume is pending after a network error, the assistant message shows a muted `Reconnecting` line in place of `network error` and hides **Retry**. The panel holds this as a union, `{ kind: "attached" } | { kind: "reconnecting"; attempt: number }`, in a small context next to `ChatIdProvider`. A provider error still shows its message and **Retry**, as today.
- **End mark.** `data-reply-end` renders as one muted line, `Stopped` or `Interrupted`, under the reply. Register it in `assistantParts` (`messages.tsx:44`). Check in turn 1 which key assistant-ui 0.15.32 uses for data part components.
- Copy stays as short labels. No helper text. Phone sizes 360 and 390 need nothing new, because these are single lines inside the existing message column.

### Boundaries

- Both new routes call `getSession`, then `getChatForUser(id, session.user.id)`, and return 404 for a chat the user does not own (`src/lib/messages.ts:265-269`). The registry checks `userId` again in `findReplyRun` and `stopReplyRun`.
- The stream route takes no body. The stop route takes no body. There is nothing to parse.
- The header name `x-resumable-stream-id` lives in one server constant, `RESUMABLE_STREAM_ID_HEADER` in `src/lib/reply-runs.ts`. Do not import it from `@assistant-ui/react-ai-sdk` in a route. That module starts with `"use client"` (`node_modules/@assistant-ui/ai-sdk/src/transport/resumable.ts:1`). A unit test asserts the two strings match.
- `discardReplyRun(chatId)` aborts the run, waits for `done`, and removes it. Slice 16 calls it before deleting the chat's rows. A save that races the delete fails safely, because `upsertMessage` returns `false` when the chat row is gone (`messages.ts:135-136`).
- Logs keep going through `sanitize` (`route.ts:146`, `route.ts:184`).

## Rules

Do:

- Keep `request.signal` away from the model, the tools, and the registry. Only the stop route and `discardReplyRun` abort a run.
- Keep one consumer of the UI stream, the pump. Every HTTP response is a listener on it.
- Test the registry with a `MockLanguageModelV3` stream from `ai/test`, as `src/lib/tools/answer-step.test.ts:4` does. Assert what a caller sees, such as "a listener that cancels does not stop the model" and "a late listener gets every chunk".
- Note in `CHANGELOG.md` that closing the tab no longer stops a reply. Stop is a button now.

Avoid:

- The `resumable-stream` package and Redis. One process, one map.
- Stopping through the fetch abort. assistant-ui stops the chat when the panel unmounts (`useChatThread.ts:304-310`), and switching chats must not kill a reply.
- Writing to the database from the pump. Only `onEnd` saves, through `upsertMessage`.
- A spinner or helper text for reconnecting. One `Reconnecting` line.
