# Slice 11: Dreaming

Once a night, read the chats that changed that day, pull out lasting facts, and merge them into memory. Users call this "dreaming" because it happens while they sleep. The job is safe to run twice, and a crash halfway through loses nothing.

**Branch** `feat/dreaming`. **Depends on** [slice 10](10.md).

## Why

After slice 10, the model saves a memory only when it decides to call `remember` mid-chat. It misses most facts, and the facts it saves pile up as near-duplicates. A nightly pass can read whole conversations, extract what matters, and merge duplicates, without slowing down any reply.

## Scope

Ships:

- A `memory_runs` table with one row per night.
- A scheduler in the server process that starts the job after 03:00 local time if tonight's run has not finished.
- `npm run dream` to run the job by hand, with `--date YYYY-MM-DD` to rerun a night.
- One model call per changed chat, which returns candidate memories.
- Merging. A candidate whose embedding is very close to an existing memory updates that memory instead of adding a new one.
- `embedPending()` from slice 10 runs at the end of each job.
- A status line at the top of `/memory` with the last run's time, chat count, added count, and merged count, or its error.

Does not ship:

- Summaries of whole chats. Only facts and preferences.
- A schedule you can change in the UI. The hour is `ORBIT_DREAM_HOUR`, default `3`.
- Deleting memories automatically.

## Design

### Data shape

```ts
type RunState = "running" | "done" | "failed";

type MemoryRun = {
	date: string; // "2026-11-02", local date, primary key
	state: RunState;
	startedAt: Date;
	finishedAt: Date | null;
	owner: string | null; // the process that holds the lease
	leaseUntil: Date | null;
	chatIds: string[]; // stored as JSON: the chats this run must process
	doneChatIds: string[]; // stored as JSON: the chats already processed
	retryChatIds: string[]; // stored as JSON: chats to try again on a later run
	added: number;
	merged: number;
	error: string | null;
};

type Candidate = { kind: "fact" | "preference"; text: string; sourceMessageId: string };
```

### The run as a state machine

| From | Event | To |
| --- | --- | --- |
| no row | the scheduler claims the date | `running` |
| `running` | every chat is in `doneChatIds` or `retryChatIds` | `done` |
| `running` | an error that is not a single chat's error | `failed` |
| `running` | `leaseUntil` has passed | claimed by a new owner, still `running` |
| `failed` | `npm run dream --date` | `running` |

The claim is one `INSERT … ON CONFLICT DO UPDATE … WHERE state = 'running' AND lease_until < :now` inside a transaction. The update sets a new `owner` and a `leaseUntil` two minutes ahead. It does not match `done` or `failed`. A `done` row stays `done` after its start time is old. A `failed` row stays `failed` until `npm run dream --date`.

Before each chat write, the owner runs `UPDATE memory_runs SET lease_until = :next WHERE date = :date AND owner = :owner`. If that updates no row, this process lost the lease and stops without writing. A live job renews the lease, so a run that lasts longer than two hours is not claimed by anyone else. Two processes cannot both hold a current lease.

### One chat

`dreamChat(chat)` in `src/lib/memory/dream.ts`:

1. It reads the chat's messages changed since the previous done run.
2. It calls `generateObject` with a zod schema for `Candidate[]` (at most 10) and a prompt that asks only for lasting facts and preferences the user stated.
3. For each candidate, it embeds the text with `kind: "document"`, like every saved memory, and looks up the nearest memory. At cosine similarity 0.9 or above, it updates that memory's text when the candidate is newer and longer, and counts a merge. Below 0.9, it adds the candidate and counts an add.
4. On success it appends the chat id to `doneChatIds` in the same transaction as the memory writes. A chat whose model call fails is appended to `retryChatIds` in that same transaction, not to `doneChatIds`.

Measured with real Ollama and the `search_document: ` label on both sides, 0.9 holds for different facts and is soft for the rest. Different facts score 0.53 to 0.58. A reworded fact scores 0.82 to 0.98, and 5 of 8 pairs reach 0.9. The same slot with another value scores 0.78 to 0.94, and "dark mode" against "light mode" scores 0.94. So cosine alone cannot tell a reworded fact from a changed one.

Step 4 makes the job idempotent. A run that restarts skips chats already in `doneChatIds`, so no memory is added twice. The run can still reach `done` when a chat fails. The run does not fail because of it. The next run's `chatIds` are the chats that changed that day plus any `retryChatIds` from the previous run. A chat that failed yesterday is retried even when it did not change again.

### Scheduler

`src/instrumentation.ts` already imports the database on the Node runtime. It also starts a 60-second interval that calls `maybeDream(now)`. That function is pure about time. It takes `now`, reads the latest run, and returns whether to start. The interval is cleared on `SIGTERM`. During `next build` no scheduler starts.

## Rules

Do:

- Write each chat's memories and its `doneChatIds` entry in one transaction.
- Pass `now` into scheduling functions, and test them with fixed dates, including the night clocks change.
- Log counts and ids. Leave memory text and message text out of logs.

Avoid:

- Running more than one model call at a time. The job is not in a hurry, and the provider may rate-limit.
- Starting the scheduler in tests or during `next build`.

## Done when

- `npm test`, `npm run typecheck`, and `npm run build` exit 0.
- After a run, facts from the day's chats show on `/memory`, and the status line shows the run.
- A second run on the same date, and a run restarted after a crash, add nothing twice.
- Near-duplicates merge.
- The scheduler starts once per night and never during a build.
