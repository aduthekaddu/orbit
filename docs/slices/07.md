# Slice 7: Web search

Let the model search the web, read the results, and answer with sources. This slice also adds the tool registry and the run card that every later tool uses.

**Branch** `feat/search`. **Depends on** [slice 3](03.md) for the browse drive.

## Why

The model knows nothing after its training cutoff and invents sources when asked for them. A self-hosted chat needs a search path that does not send every query to one vendor. SearXNG is a search engine you run yourself. Tavily is a hosted search API for people who do not want to run SearXNG.

Today the chat route stops after one model step (`stepCountIs(1)`). A tool can run, but the model never sees its result, so it cannot answer from it. Every tool after this one needs a call-then-answer loop, which makes this slice the place to build it.

## Scope

Ships:

- A tool registry in `src/lib/tools/`. `render_ui` moves into it unchanged.
- A step limit of 5, so the model can call tools and then answer.
- A `web_search` tool backed by SearXNG, Tavily, or both.
- Settings for the SearXNG URL and the Tavily key. The key follows the provider key's rules. It is stored on the server, and the browser only learns `tavilyKeySet`.
- A run card for every tool call. It shows running, succeeded, failed, or cancelled. Search results render as a list of links inside it.
- A `searxng` service in `docker-compose.yml`, bound to `127.0.0.1:8888`, with JSON output turned on.

Does not ship:

- Fetching and reading full pages. The model gets titles, URLs, and snippets.
- Streaming partial results into the card before the search finishes.
- A favicon fetch. The card shows the domain's first letter in a bordered square.

## Design

### Data shape

```ts
type SearchResult = {
	title: string;
	url: string; // absolute http or https only
	snippet: string; // plain text, at most 300 characters
	engine: "searxng" | "tavily";
};

type SearchOutput =
	| { ok: true; query: string; results: SearchResult[] } // at most 8 results
	| { ok: false; query: string; error: string };

type ToolRunStatus = "running" | "succeeded" | "failed" | "cancelled";
```

The client derives `ToolRunStatus` from the AI SDK tool part. The server sends no second copy.

| Tool part state | Run status |
| --- | --- |
| `input-streaming`, `input-available` | `running` |
| `output-available` | `succeeded` |
| `output-error` | `failed` |
| The turn was stopped before output | `cancelled` |

### Tool registry

```ts
type ToolEntry = {
	name: string;
	enabled: (settings: SettingsRecord) => boolean;
	create: (settings: SettingsRecord) => Tool;
	card: "genui" | "search" | "generic"; // which React body renders the output
};
```

`src/lib/tools/index.ts` holds the entries and exports `toolsFor(settings)`. The route calls it in place of `chatTools`. `web_search` is enabled when the SearXNG URL or the Tavily key is set. The client maps `card` to a component in `src/components/tools/`. A tool name with no entry renders the generic card with the JSON output behind a disclosure, and the thread keeps working.

### Search backends

`searchSearxng(url, query, signal)` calls `GET {url}/search?q=…&format=json`. `searchTavily(key, query, signal)` calls `@tavily/core`. Each parses the response with zod into `SearchResult[]`. Each strips HTML from snippets, drops results without an http or https URL, and removes duplicate URLs. Each times out after 8 seconds.

When both backends are set, SearXNG runs first and Tavily runs only if SearXNG fails or returns nothing. A failure returns `{ ok: false, error }`. It never throws, so the model can say the search failed.

### Prompt

Add one sentence to the instructions when `web_search` is enabled: "Use web_search for recent events, prices, or facts you are unsure of. Cite sources as markdown links to result URLs."

### Settings

One migration adds `settings.searxng_url` and `settings.tavily_api_key`. Both default to an empty string. `toPublicSettings` returns `searxngUrl` and `tavilyKeySet`. The settings form adds a **Search** section with the two fields. A blank key field keeps the stored key, using the same rule as the provider key.

## Rules

Do:

- Parse every backend response with zod at the boundary, and trust `SearchResult` after that.
- Render result titles and snippets as text, and give links `rel="noopener noreferrer nofollow"` and `target="_blank"`.
- Keep `render_ui` working. The genui tests and `scripts/smoke-genui.ts` must still pass.

Avoid:

- Returning the Tavily key or the provider key in any response or log line.
- Raising the step limit above 5. A loop that runs longer costs money and time with no gain for this slice.

## Build

### Turn 1. Reproduce, then write failing tests

1. Reproduce. With the real provider, ask "What happened in the news today?" and save the answer. It cannot search, so it either refuses or guesses. Save `before.png`.
2. Write `search-tool.mjs`. Start `mock-searxng.mjs`, save its URL in settings, send `[qa:search] orbit`, and check for a run card that goes from running to succeeded, three result links, and an answer that links the first result URL. Reload and check that the card and links are still there. Run it on `main`. It must fail.
3. Write `search.test.ts`. Parse a recorded SearXNG response and a recorded Tavily response. Check that HTML is stripped, a `javascript:` URL is dropped, duplicates are removed, a timeout returns `ok: false`, and Tavily runs only after SearXNG fails. Write `run-status.test.ts` for the table above. Run `npm test`. The new tests must fail.

### Turn 2. Make the tests pass

1. Build the registry and move `render_ui` into it. Run the genui tests before going on.
2. Build the backends, the tool, and the settings.
3. Build the run card, the search body, and the generic body.
4. Add the `searxng` service and start it once to check that `curl '127.0.0.1:8888/search?q=test&format=json'` returns JSON.
5. Run `npm test`, `npm run typecheck`, and `npm run build`.

### Turn 3. Prove it with verify-orbit

1. Run `launch --mock`, `doctor`, `browse search-tool`, and `cleanup`.
2. With the real provider and the compose SearXNG, ask the same news question as turn 1 and screenshot the card and the answer.
3. Stop SearXNG and ask again. Screenshot the failed card and the model's reply.
4. Measure the time to the final answer for 5 real search questions. Report p50 and the slowest. No budget gates this number, because it depends on the provider and the search engines. Record it as the baseline for later slices.
5. Post the output and the screenshots, update the changelog and the roadmap, and mark the PR ready.

## Done when

- `npm test`, `npm run typecheck`, and `npm run build` exit 0. The genui smoke still passes.
- The model calls `web_search`, reads the results, and answers with links to them.
- The run card shows running, succeeded, failed, and cancelled. A reload shows the same card.
- A search failure shows a failed card, and the model still answers.
- `GET /api/settings` never contains the Tavily key.
