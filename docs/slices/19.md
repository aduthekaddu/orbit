# Slice 19. Tools page and tools sheet

Show every tool Orbit can give the model on one page, prove each one works with a real call, and let each chat turn tools off. This is gap G6 in the gap analysis and step 5 of the v1 plan.

**Branch** `feat/tools-page`. **Depends on** slice 18 for roles, `instance_settings`, the per-user GitHub token, and per-user memories. It reuses the per-chat write path and the popover and sheet from slice 17, and the plain tool names from slice 15.

## Why

Today a tool is on or off because of a settings row and an environment variable. `toolsFor` in `src/lib/tools/index.ts:35` turns on `web_search` when a SearXNG URL or Tavily key is saved, `run_code` when the server sets `ORBIT_SANDBOX=on` (`src/lib/sandbox/enabled.ts:1`), `remember` and `forget` always, and `render_ui` always. `toolsForTurn` at `src/lib/tools/index.ts:43` adds the `github_*` tools when a token is saved. Nobody can see that list.

Only GitHub has a check, the **Check** button in Settings (`src/components/settings/settings-form.tsx:291`, route `src/app/api/settings/github/check/route.ts:15`, which calls `checkGithub` at `src/lib/tools/github.ts:200`). The sandbox shows only On or Off from the environment (`settings-form.tsx:313`). Search and memory have no check at all. A user learns that search is broken when an answer comes back without sources.

A chat cannot turn a tool off. A user who wants a plain answer without a web search, or who does not want GitHub tools offered in a chat about something else, has no switch. ChatGPT and Claude.ai both put tools behind a **+** menu in the composer.

## Scope

Ships:

- A `/tools` page that lists Web search, Code sandbox, GitHub, Memory, and Generated UI. Each row shows its status, the time of its last good call, and the exact tool names, descriptions, and input schemas the model receives.
- A **Test** button on every tool except Generated UI. It makes one real minimal call. Web search runs a fixed query. The sandbox runs `print(1)`. GitHub calls `get_me`. Memory reads the user's memories.
- A record of the last good call and the last failure per user and tool, written by tests and by real chat calls.
- A **+** button in the composer that opens a tools sheet with one switch per available tool. The choice is stored on the chat.
- A **Tools** link in the sidebar drawer and the command palette.

Does not ship:

- New tools. Slice 23 adds remote MCP servers to this page and to the sheet.
- Moving tool configuration out of Settings. The page links to the Settings section that configures each tool.
- A per-user default set of tools for new chats. Every new chat starts with every available tool on.
- Turning Generated UI off. `searchAnswerStep` in `src/lib/tools/answer-step.ts:14` forces `activeTools: ["render_ui"]` on the last step, and artifacts rely on it.

## Design

### Data shape

The user-facing unit is a tool id. Most ids are the model tool name. GitHub and Memory group several model tools under one id.

```ts
// src/lib/tools/metadata.ts, browser-safe
type ToolId = "web_search" | "run_code" | "github" | "memory" | "render_ui";

// Which ToolId owns a model tool name. "github_list_issues" -> "github", "remember" -> "memory".
function toolIdFor(modelToolName: string): ToolId | null;

// src/lib/tools/status.ts, server only
type ToolScope = "instance" | "personal" | "built-in";

type ToolSetup =
  | { state: "ready" }
  | { state: "missing"; configure: "admin" | "self" } // no search backend, no GitHub token
  | { state: "server-off" };                           // ORBIT_SANDBOX is not "on"

type ToolHealth =
  | { state: "untested" }
  | { state: "working"; lastGoodAt: Date }
  | { state: "failing"; lastGoodAt: Date | null; failedAt: Date; error: string };

type ToolView = {
  id: ToolId;
  scope: ToolScope;
  setup: ToolSetup;
  health: ToolHealth;
  canTest: boolean;
  configureHref: string | null; // null when the viewer may not configure it
};

type CheckResult =
  | { ok: true; ms: number; summary: string } // "3 results", "Exit 0", "octocat", "12 memories"
  | { ok: false; ms: number; error: string };
```

`scope` is fixed per tool. Web search and Code sandbox are `instance` because their config lives in `instance_settings`. GitHub and Memory are `personal` because slice 18 keys the token and the memories by user. Generated UI is `built-in`.

The status word on the page derives from `setup` first, then `health`: **Off**, **Not tested**, **Working**, or **Failing**. One pure function, `toolView(id, setupInput, row, viewer)`, builds a `ToolView`. Nothing else decides a status.

### Storage

One new table in `src/lib/db/schema.ts`, `tool_status`:

| Column | Type | Notes |
| --- | --- | --- |
| `user_id` | text NOT NULL | References `user.id`, `ON DELETE CASCADE` |
| `tool_id` | text NOT NULL | One of `ToolId` |
| `last_ok_at` | integer, nullable | `timestamp_ms` |
| `last_failed_at` | integer, nullable | `timestamp_ms` |
| `last_error` | text, nullable | A fixed user-facing message, at most 200 characters |

The primary key is `(user_id, tool_id)`. Health comes from the two timestamps. No row means `untested`. `last_failed_at` newer than `last_ok_at` means `failing`. Otherwise `working`. Two timestamps cannot disagree the way a boolean plus a timestamp can.

`last_error` holds only the messages the tools already return to users, such as `Search is unavailable` (`src/lib/tools/search.ts:122`), `GitHub rejected the token.` (`github.ts:70`), and the sandbox messages in `src/lib/tools/run-code.ts:17-20`. Never store exception text. It can carry a URL or a token.

Every row is the viewer's own. The page never reads another user's rows, so a member never learns when someone else used search. The query helpers in `src/lib/tools/status.ts` take `userId` first, as the contract requires.

The per-chat choice is a new column on `chats`, `disabled_tools`, text NOT NULL default `'[]'`. It holds a JSON array of ids that are off in that chat. Storing the off list means a tool configured later is on in old chats. Slice 23 adds ids of the form `mcp:<serverId>` to the same array, so the parser accepts `ToolId` or that pattern and drops anything else. Parse it with zod where the row is read, in `src/lib/messages.ts`, and trust the type after that.

### What the model sees

`GET /api/tools/[id]` returns the model tools for that id. It builds them with the same `toolsForTurn` the chat route uses at `src/app/api/chat/route.ts:99`, filters by `toolIdFor`, and converts each `inputSchema` with `asSchema(tool.inputSchema).jsonSchema` from `ai`. That property can be a promise, so await it. The result is `{ name, description, inputSchema }[]` plus the instruction line the chat route adds for that tool (`route.ts:118-119`), so the page shows every word the model gets about the tool.

The AI SDK sends that same JSON Schema to an OpenAI-compatible provider. That is inferred from how the SDK prepares tools. The turn 3 scenario checks it against the `tools` array the mock provider logged.

For GitHub this opens the MCP client, so the page fetches it only when a row is expanded. `githubTools` caches the list for five minutes (`github.ts:18`).

### Checks

`runToolCheck(userId, id, signal, deps)` in `src/lib/tools/checks.ts` makes one real call per tool and records the outcome in `tool_status`. `deps` defaults to the real functions so tests can inject fakes, the way `searchWeb` takes `backends` at `src/lib/tools/search.ts:97`.

| Tool | Call | Good when | Summary |
| --- | --- | --- | --- |
| Web search | `searchWeb(searchSettings, "orbit", signal)` | `ok: true` with at least one result | `3 results` |
| Code sandbox | `runCode(sandboxDocker(), { language: "python", code: "print(1)" }, signal)` | `exitCode === 0` and `stdout.trim() === "1"` | `Exit 0` |
| GitHub | `checkGithub({ token, mcpUrl }, signal)` | `ok: true` | the login |
| Memory | `memoryCount` for the user, then `ollamaStatus()` | the count query returns | `12 memories`, plus `Text search only` when Ollama is down |

Memory with Ollama down still counts as working. Recall falls back to full-text search in that case, as slice 10 designed.

Each check has a 15-second ceiling through `AbortSignal.any([request.signal, AbortSignal.timeout(15_000)])`. A user can run one check per tool at a time and one every 10 seconds. The limit is a `Map` keyed by `userId` and `id` in `checks.ts`. Orbit is one process, so memory is enough. A second request inside the window gets `429`.

### Recording real calls

`toolsForTurn` wraps each tool's `execute` with `recordingTool(tool, id, userId)`. After `execute` resolves, it reads the outcome with `toolRunStatus({ state: "output-available", output }, false, name)` from `src/lib/tools/run-status.ts:10`. That is the same rule the run card uses, so the page and the card always agree on what failed. `succeeded` sets `last_ok_at`. `failed` sets `last_failed_at` and `last_error` from the output's `error` string. A thrown error records `failed` only when the request was not aborted. `cancelled` records nothing.

### Per-chat switches

`toolsForTurn(settings, stopped, source, signal)` gains `disabled: readonly string[]`. It skips a disabled entry before calling `create`. With `github` disabled it does not call `openGithubTurn`, so no MCP client opens.

With `memory` disabled in a chat, the route also skips `recall` at `route.ts:112`. A chat with memory off should not quietly read memories. When the user's memory preference from slice 18 is off, Memory does not appear in the sheet at all.

`convertToModelMessages(uiMessages, { tools })` at `route.ts:131` still receives earlier tool parts for a tool that is now off. The SDK converts those parts without the tool definition. That is inferred. Turn 1 tests it.

The sheet writes through the same path slice 17 uses for the chat's model. Slice 16 adds `PATCH /api/chats/[id]` for rename, and slice 17 may extend it. Add `disabledTools` to that route's zod schema. If neither slice added the route, add the `PATCH` here with the ownership check from `getChatForUser` (`src/lib/messages.ts:265`). If slice 16 made chat rows appear only on the first message, follow whatever slice 17 does for a model chosen before that. A change applies from the next turn. A turn that is streaming keeps the tools it started with.

### Who may do what

| Action | Admin | Member |
| --- | --- | --- |
| See every row and its schemas | Yes | Yes |
| Test Web search or Code sandbox | Yes | Yes |
| Configure Web search or Code sandbox | Yes, link to the admin section of Settings | No. The row shows status only. |
| Test and configure their own GitHub and Memory | Yes | Yes |
| Turn tools off in their own chat | Yes | Yes |

A member may test an instance tool because the test does nothing a chat turn cannot do. Any member can already make the model run a search. The rate limit covers repeated presses. Configuring stays admin-only. The routes that save search and sandbox config are slice 18's admin routes, and this slice adds no new write route for them.

In `community` mode the admin's search backend and sandbox serve every member, the same as in `team`. That spends the admin's Tavily credits and runs strangers' code in the sandbox. This plan keeps the simple rule and leaves a per-tool admin switch for members to the maintainer. Generated UI stays always on for the same kind of reason. The search answer step and artifacts depend on it.

### The page

`/tools` sits in the app shell at the width of `/settings`. One bordered list, one row per tool. A row shows the tool's plain name from slice 15, a status dot and word, the last good call as a relative time in `num` such as `4 min ago`, and a **Test** button. While a test runs the button shows `OrbitMark` busy and is disabled. After it ends the row shows the summary or the error in `text-destructive` until the next test. An Off row shows **Set up** instead of **Test** when `configureHref` is set, and nothing when it is not.

Tapping the row name expands it. The expanded row lists each model tool name in `font-mono`, its description, and its input schema as formatted JSON. Render the JSON with `SyntaxHighlighter` from `src/components/chat/code-block.tsx:150` and language `json`, so long schemas get the line cap and the sideways `ScrollFade`. It calls `useCodeEdit()`, which has no provider outside a chat. Confirm it renders read-only there, which is inferred from the code. Below that sits the instruction line, when the tool has one.

At 360px and 390px each row stacks. The name and status sit on one line, the time and **Test** on the next. The schema well scrolls sideways under its fade and never widens the page. On desktop the row is one line.

Status colors use `--positive`, `--destructive`, and `--muted-foreground`. No new tokens.

### The sheet

A **+** icon button sits at the left of the composer's action row (`src/components/chat/composer.tsx:28`), before the model control from slice 17. It has `aria-label="Tools"`. It opens the popover slice 17 built for the model picker on desktop, and the bottom sheet on `pointer: coarse` or under 640px.

The sheet lists only tools whose `setup` is `ready`, each with its plain name and a switch. Generated UI is not listed. A last row links to **Tools**. When every tool is off except Generated UI, the sheet still opens and shows the switches. When no tool is available it shows only the **Tools** link.

The switch is a new `src/components/ui/switch.tsx`, a `button` with `role="switch"` and `aria-checked`, sized and colored from tokens. No new package. Toggling saves at once and rolls back with a one-line error if the save fails.

## Rules

Do:

- Derive every status from `toolView`. The page, the sheet, and the API read it.
- Record outcomes with the run card's rule, `toolRunStatus`. Do not write a second definition of failure.
- Keep every `tool_status` read scoped to the viewer.
- Return no secret from any new route. A `ToolView` has no URL, token, or key in it.
- Specify each layout at 360px, 390px, and desktop, and screenshot all three.

Avoid:

- Connecting to GitHub from `GET /api/tools`. Only the expanded row and the test do that.
- Storing raw error messages.
- A second tool registry. The page builds from `toolsForTurn`, so it cannot drift from what the chat sends.
- Helper text on the page or the sheet. Labels only.
