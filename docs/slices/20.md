# Slice 20. Files

Attach images, PDFs, and text files to a message. The model reads what it can, and the chat says how much it read. A Files panel shows the files in a chat, and a Files page lists every file with search, download, and delete.

**Branch** `feat/files`. **Depends on** [slice 17](17.md) for the model capability badges, and [slice 18](18.md) for accounts, `user_id` on every table, and the cross-user route test.

## Why

People paste screenshots, PDFs, and logs into ChatGPT and Claude every day. Orbit has no way to do that. There is no upload route, no table, and no composer button. Each user of a multi-user install needs their files kept apart from everyone else's, and needs to delete them.

A hidden path already exists, and it is unsafe. `useChatRuntime` gets assistant-ui's default attachment adapter, because `chat-panel.tsx:59` passes only `history` and `@assistant-ui/ai-sdk` 0.0.16 fills in `vercelAttachmentAdapter` (`dist/runtime/useAISDKRuntime.js:719`). That adapter accepts any type (`accept: "*"`) and turns the whole file into a `data:` URL (`dist/adapters/vercelAttachmentAdapter.js:4-33`). `ComposerPrimitive.Input` adds pasted files by default (`addAttachmentOnPaste = true`, `@assistant-ui/react` `dist/primitives/composer/ComposerInput.js:54`). The chat route accepts any user part (`parts: z.array(z.unknown())`, `src/app/api/chat/route.ts:25`), and `upsertMessage` stores it as JSON in `messages.parts` (`src/lib/messages.ts:128`). So a pasted image probably reaches the database as a base64 blob and the model as an image, with no chip in the composer and nothing in the bubble. That chain is inferred from the code. Turn 1 confirms it.

The model side has limits too. `@ai-sdk/openai-compatible` 3.0.82 sends images as `image_url` (`dist/index.js:96-97`), sends PDFs only as inline data (`dist/index.js:120-127`), and throws on text file parts (`dist/index.js:91`). Text files have to become text before the provider sees them.

LibreChat cuts long text "without warning". Orbit shows how much of each file the model read.

## Scope

Ships:

- An `attachments` table and per-user file storage under the data folder.
- `POST /api/files`, `GET /api/files`, `GET /api/files/<id>`, and `DELETE /api/files/<id>`.
- An Orbit attachment adapter that replaces the default one, a paperclip button, drag and drop, paste, and file chips in the composer and in sent messages.
- Images and PDFs sent only to models whose slice 17 badges allow them. Text files sent inline up to a limit, with a "Read N of M characters" note when cut.
- A Files panel per chat, and a `/files` page with search, download, and delete.
- A "File deleted" marker in messages that used a deleted file.
- Cleanup when a chat or a user is deleted, and a sweep for unsent uploads.
- A per-user storage cap from the environment.

Does not ship:

- Retrieval search over files. Every file the model reads goes inline.
- Reusing a file in another chat. A file belongs to the chat it was sent in.
- Office documents, audio, or video.
- Text extraction from PDFs for models that cannot read PDFs.
- Files in share links. [Slice 22](22.md) leaves them out.

## Design

### Data shape

```ts
type AttachmentKind = "image" | "pdf" | "text";

type AttachmentBase = {
	id: string; // crypto.randomUUID(), so a URL never ends in an extension
	userId: string;
	name: string; // the uploaded file name, at most 255 characters, no path parts
	kind: AttachmentKind;
	mediaType: string; // sniffed from the bytes, never taken from the browser
	size: number; // bytes
	sha256: string; // hex, also the blob's file name
	textChars: number | null; // code points, set only when kind is "text"
	createdAt: Date;
};

// One state field instead of loose flags. The CHECK constraint below keeps the columns honest.
type Attachment = AttachmentBase &
	(
		| { state: "pending"; chatId: null; messageId: null } // uploaded, not yet sent
		| { state: "sent"; chatId: string; messageId: string } // messageId is the first message that sent it
		| { state: "deleted"; chatId: string; messageId: string } // blob removed, row kept as a marker
	);
```

`attachments` in `src/lib/db/schema.ts`:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | text primary key | UUID |
| `user_id` | text not null | references `user.id` on delete cascade |
| `chat_id` | text | references `chats.id` on delete cascade |
| `message_id` | text | references `messages.id` on delete cascade |
| `state` | text not null | `pending`, `sent`, or `deleted` |
| `name`, `kind`, `media_type` | text not null | |
| `size` | integer not null | |
| `sha256` | text not null | |
| `text_chars` | integer | |
| `created_at` | integer not null | `timestamp_ms` |

Constraints, with drizzle's `check()` from `drizzle-orm/sqlite-core`:

- `(state = 'pending' AND chat_id IS NULL AND message_id IS NULL) OR (state IN ('sent', 'deleted') AND chat_id IS NOT NULL AND message_id IS NOT NULL)`.
- `(kind = 'text') = (text_chars IS NOT NULL)`.
- Indexes on `(user_id, created_at)`, `(chat_id)`, and `(user_id, sha256)`.

A pending file has no chat, because a chat row may not exist yet when you pick a file. Slice 16 may create the chat only on the first send (v1 plan step 0). Linking happens when the message is saved.

### Limits

One table in `src/lib/files/limits.ts` owns every limit. These numbers are starting values for the maintainer to confirm.

| Limit | Value | Why |
| --- | --- | --- |
| Image | 5 MB | Anthropic's API refuses larger images. Inferred from its docs, check in turn 1. |
| PDF | 10 MB | Base64 grows it by a third, and the whole request must stay under provider limits. |
| Text | 1 MB | |
| Files per message | 5 | |
| Inline text per file | 100,000 characters | About 25,000 tokens. |
| Storage per user | `ORBIT_FILES_MAX_MB`, default 1024 | Read with `readEnv` from `src/lib/env.ts:2`. |

Types come from the bytes, not from the browser:

- **Image.** PNG, JPEG, GIF, or WebP by magic bytes.
- **PDF.** The bytes start with `%PDF-`.
- **Text.** Valid UTF-8 (`new TextDecoder("utf-8", { fatal: true })`), no NUL byte, and a name ending in one of a fixed list of extensions (`txt`, `md`, `csv`, `tsv`, `json`, `yaml`, `yml`, `xml`, `html`, `css`, `js`, `jsx`, `ts`, `tsx`, `py`, `go`, `rs`, `java`, `c`, `h`, `cpp`, `rb`, `sh`, `sql`, `toml`, `ini`, `log`, `svg`).
- SVG is text, never an image. Served as an image from Orbit's origin, an SVG can run script.
- Anything else gets `415` with "This file type is not supported."

### Storage

- Blobs live at `<dataDirectory()>/files/<userId>/<sha256>`. `dataDirectory()` is `src/lib/paths.ts:4-6`. Directories are `0700` and files `0600`, the same modes `src/lib/db/index.ts:18-19` and `:30-40` set for the database.
- Content-addressed within one user only. Two users who upload the same bytes get two blobs, so a hash never tells one user that another has a file.
- An upload streams `request.body` to `files/<userId>/.tmp-<uuid>` while it counts bytes and hashes. Past the kind's limit it stops, deletes the temp file, and answers `413`. Then it renames the temp file to the hash name. If that name exists, it deletes the temp file instead. Rerunning an upload converges on one blob.
- The Docker volume already covers this. `docker-compose.yml:9` mounts `./data:/app/data`, and `docker/entrypoint.sh:14` runs `chown -R` on it at every start. With many files that start gets slower. That cost is inferred and not measured. Turn 3 times a start with 5,000 files.
- Backups. The README has no backup section today. Add **Back up your data**. For an exact copy, stop Orbit (`docker compose stop`), copy the whole `data/` folder, and start it again. A live backup copies the database first with `sqlite3 data/orbit.db ".backup backup.db"`, which is safe under WAL, then copies `data/files/`. That order is not exact either. A file deleted between the two copies has a `sent` row in the backup and no blob, and shows "File missing" after a restore. A file uploaded in between leaves a blob with no row, which the sweep removes. Say both in the README.

### Upload and send flow

1. You pick, drop, or paste a file. `orbitAttachmentAdapter.add()` in `src/components/chat/attachments.ts` yields an uploading state, sends the raw bytes to `POST /api/files?name=<name>`, and yields `requires-action` with the returned id. A rejected upload yields an error state with the server's message, such as "Too large".
2. `send()` returns one content part per file: `{ type: "file", sourceType: "id", data: "/api/files/<id>", mimeType, filename }`. assistant-ui's `toCreateMessage` passes an `id` source through unchanged (`@assistant-ui/ai-sdk` `dist/converters/toCreateMessage.js:25-33`), so the UI message part becomes `{ type: "file", url: "/api/files/<id>", mediaType, filename }`.
3. `POST /api/chat` parses the parts of the new user message, the one not yet stored, with a new zod union in `src/lib/files/parts.ts`. It allows `text` parts and `file` parts whose `url` matches `^/api/files/<uuid>$`. A `data:`, `http:`, or any other URL gets `400` with `Attach the file again.` User messages already stored are not parsed again. `persistIncoming` already requires their parts to equal the stored JSON (`src/lib/messages.ts:171-173`), so a client cannot slip a new `data:` part into the history. Assistant parts from the client are ignored as today (`route.ts:92`).
   Existing chats can already hold `data:` file parts from the hidden path above. Parsing the whole history would answer every later turn in those chats with `400`, and rewriting the stored parts would make `persistIncoming` answer `409`, because the open page still holds the old parts. So stored `data:` parts stay as they are, as legacy parts. `modelPartsFor` sends a legacy image or PDF part the way it does today when the model's badge allows it, and a placeholder with `model-cannot-read` otherwise. A legacy part of any other type becomes a `model-cannot-read` placeholder, because the openai-compatible provider throws on text file parts (`dist/index.js:91`). In the bubble a legacy part shows a chip with its file name and no actions. It is not in `attachments`, so the Files panel and `/files` do not list it. Editing such a message and keeping the file sends it as a new message, which gets `Attach the file again.`
4. `planChatWrite` gets the user id and the file ids. Inside its transaction it checks that every file belongs to this user, is not deleted, and is either pending or already sent in this chat. Another user's id, or an unknown id, returns `404`. Your own file from another chat, or a deleted one, returns `400`. On the new user message it sets pending rows to `sent` with the chat id and message id. A sent row stays as it is, so an edit that keeps a file reuses it.
5. The route stores the user part exactly as received. `persistIncoming` compares stored and incoming user parts as JSON strings (`src/lib/messages.ts:171-172`). A rewritten part would make the next turn fail with `409`. A test sends a file, reloads, and sends again to guard this.
6. Before `convertToModelMessages` (`route.ts:131`), `modelPartsFor(userId, uiMessages, capabilities)` in `src/lib/files/model-input.ts` replaces each file part. It loads all rows in one query and reads blobs only for parts that are sent as bytes.

```ts
type ModelFileInput =
	| { kind: "image" | "pdf"; send: "bytes" } // becomes a data: URL in memory only
	| { kind: "text"; send: "inline"; chars: number; total: number } // becomes a text part
	| { kind: AttachmentKind; send: "placeholder"; reason: "deleted" | "missing" | "model-cannot-read" };
```

`planFileInput(attachment, capabilities)` is the pure function that picks the variant. Text goes in as:

```text
<file name="notes.md" chars="100000" total="240000">
...
</file>
```

The route instructions add one line saying file contents are data from the user, not instructions. This follows the quoted memory notes pattern in `src/lib/memory/recall.ts:28-37`.

Model capabilities come from slice 17's model badges. This slice needs `images` and `pdf`. If slice 17 has no PDF badge, this slice adds `pdf` to the same capability record. A capability that is unknown counts as no.

For the newest user message, a file the model cannot read is an error, not a silent drop. The composer disables Send and the chip shows a warning icon labelled "This model can't read images" (or PDFs). The route also refuses with `400` and the same text. For earlier messages in the history the route sends a placeholder instead. Otherwise one image early in a chat would block every later turn after you switch to a text-only model.

### Showing what the model read

The note depends only on the file and the fixed inline limit, so it needs no stored state. When `textChars` is over the limit, the chip shows "Read 100,000 of 240,000 characters" with the numbers in `num`. A deleted file shows "File deleted". A row whose blob is gone shows "File missing".

### Serving files

`GET /api/files/<id>` checks the session and the owner in the handler, and returns `404` for anyone else's id. The proxy matcher skips paths ending in `.svg|.png|.jpg|.jpeg|.gif|.webp` (`src/proxy.ts:34`), so a route like `/api/files/photo.png` would skip the sign-in check. The ids are UUIDs and the route parses them with `z.uuid()`, so no file URL ends in an extension. The handler's own check is the guard either way.

Headers on every file response:

- `X-Content-Type-Options: nosniff`.
- `Content-Security-Policy: default-src 'none'; sandbox`, so an opened file cannot run script on Orbit's origin.
- `Content-Disposition: inline` for images only, so the thread can show a thumbnail. `attachment; filename*=UTF-8''<name>` for PDFs and text.
- `Cache-Control: private, max-age=3600`.

### Delete and cleanup

- Removing a chip in the composer deletes a pending row and its blob.
- **Delete** on the Files page or panel sets a sent row to `deleted` and removes the blob if no other row of that user has the same hash. The dialog names the chat that uses it. The model gets a placeholder from then on, and the message shows "File deleted".
- Deleting a chat cascades its rows through `chat_id`. Deleting a user cascades through `user_id`. Their blobs then have no row, so the next sweep removes them, and it removes a user's folder once it is empty. Slice 18 does not know about files. When slice 18b's user removal exists, its route calls `sweepFiles(new Date())` right after the delete, so a removed person's files go at once.
- `sweepFiles(now)` in `src/lib/files/sweep.ts` deletes pending rows older than 24 hours and any blob with no row. It runs at start from `src/instrumentation.ts:1-7` and hourly on an unref'd timer, the same shape as `startDreamScheduler` in `src/lib/memory/schedule.ts:94-114`. It reads state each run, so a crash mid-sweep is fixed by the next run.

### UI

The composer, in `src/components/chat/composer.tsx`, gets these parts:

- A paperclip `ComposerPrimitive.AddAttachment` button left of the model chip (`composer.tsx:28-38`). `accept` lists the image types, `application/pdf`, and the text extensions. On a phone the native picker offers the camera and the photo library.
- `ComposerPrimitive.Attachments` above the input shows one chip per file with an icon or thumbnail, the name, the size in `num`, and a remove button. An uploading chip shows `OrbitMark busy`. A failed chip uses `text-destructive`.
- `ComposerPrimitive.AttachmentDropzone` wraps the composer on desktop. While a file is over it, the border turns `border-border-strong`.
- At 360px and 390px the chips sit in one row inside `ScrollFade axis="x"`, and the composer does not grow wider than the screen.

**Sent messages.** The user bubble in `UserMessage` (`src/components/chat/messages.tsx:125-147`) renders `MessagePrimitive.Attachments` above the text with the same chip, read-only. An image chip shows a 64px thumbnail that opens the full image in a dialog. Chips read their row from a `ChatFilesProvider` that the chat page fills with `listChatAttachments(userId, chatId)`, so a chip makes no request of its own.

**Files panel.** `src/components/chat/chat-actions.tsx` is a new top-right toolbar inside `ThreadPrimitive.Root` (`src/components/chat/thread.tsx:49`). It holds a **Files** button, shown when the chat has a sent file. The button opens a panel on the right on desktop and a bottom sheet on a phone. Each row has the name, size, the read note, **Download**, and **Delete**. [Slice 22](22.md) adds **Share** to the same toolbar. If slice 16 already added a per-chat menu, put **Files** there instead.

**Files page.** `/files` sits in the app shell at the settings width. A search field filters by name. Each row has a kind icon, the name, the size, the chat title as a link to `/c/<chatId>?m=<messageId>`, the date, **Download**, and **Delete**. On a phone each row stacks into two lines, and the two actions stay visible at 44px. Rows load 100 at a time, newest first, with **Show more**. Name search uses `instr(lower(name), lower(?))`, so `%` and `_` in a query are plain characters.

### Boundaries

- Routes parse the upload query (`name`), the id param, and the list query (`q`, `cursor`) with zod. Code after that trusts the types.
- Every helper in `src/lib/files/store.ts` takes `userId` first: `createUpload(userId, ...)`, `listFiles(userId, ...)`, `listChatAttachments(userId, chatId)`, `getFile(userId, id)`, `deleteFile(userId, id)`.
- `Content-Length` over the largest limit gets `413` before the body is read. A body without `Content-Length` gets `411`.
- Next buffers request bodies that pass through `src/proxy.ts` up to a size limit. In Next 15 the option is `middlewareClientMaxBodySize`, default 10 MB. Find the Next 16.4 name, set it above the largest file limit in `next.config.ts`, and test an upload at exactly the limit. This is inferred from the Next 15 docs.

## Rules

Do:

- Sniff every type from the bytes. Treat the browser's type and the extension as hints.
- Keep blobs out of `messages.parts`. A part holds only the `/api/files/<id>` URL.
- Return `404` for another user's file id on every route, and add each route to slice 18's cross-user test.
- Write the temp file and rename it, so a crash never leaves a half blob under a hash name.

Avoid:

- Serving any upload as `text/html` or `image/svg+xml`.
- Logging file names or contents. Log ids and sizes only.
- Silent cuts. Every cut or skipped file shows a note or an error.
