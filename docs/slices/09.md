# Slice 9: GitHub

Let the model read your GitHub repositories, issues, and pull requests through GitHub's MCP server. MCP, the Model Context Protocol, is a standard way to hand a model a set of tools from another service. This slice is read-only.

**Branch** `feat/github-mcp`. **Depends on** [slice 7](07.md) for the tool registry and the run card.

## Why

A developer asks "what changed in PR 42?" or "which open issues mention the migration lock?" and today has to paste the answer in by hand. GitHub publishes an MCP server with these tools. The AI SDK's MCP client turns them into ordinary tools, so Orbit gets them without writing a GitHub client.

## Scope

Ships:

- A GitHub token setting. It follows the provider key's rules. It is stored on the server, and the browser only learns `githubTokenSet`.
- GitHub's remote MCP server connected through `@ai-sdk/mcp`, in read-only mode, limited to the repository, issue, and pull request toolsets.
- GitHub tools in the registry with the prefix `github_`, so they cannot collide with Orbit's own tool names.
- A GitHub body for the run card that turns issue, PR, and file results into links. Other results use the generic card.

Does not ship:

- Write tools such as creating issues, commenting, or merging. They need an approval step in the UI first.
- OAuth sign-in with GitHub. The user pastes a fine-grained personal access token.
- Running GitHub's MCP server locally in Docker.

## Design

### Data shape

```ts
type GithubSettings = {
	token: string; // server only
	mcpUrl: string; // default "https://api.githubcopilot.com/mcp/"
};

type McpToolSet = {
	tools: Record<string, Tool>; // names already prefixed with github_
	close: () => Promise<void>;
};
```

### Connecting

`githubTools(settings)` in `src/lib/tools/github.ts` calls `createMCPClient` from `@ai-sdk/mcp` with an `http` transport, the token as a bearer header, and the read-only and toolset settings. It calls `client.tools()`, prefixes each name, and returns the tools with a `close` function.

GitHub's documentation sets read-only mode and toolsets through request headers or the URL. Turn 1 reads the current [github-mcp-server README](https://github.com/github/github-mcp-server) and records the exact header names and values in the PR. Do not guess them.

The route calls `githubTools` only when a token is set. It closes the client in `onEnd` and in the error path, so no connection is left open. The tool list is cached in memory for 5 minutes per token, so most turns skip the list request. A tool call still goes to GitHub every time.

### Failure

If GitHub is unreachable or the token is wrong, the turn still runs without GitHub tools. The server logs one sanitized line. The settings page shows the result of the last connection check: **Connected** with the GitHub login, or the error text.

`POST /api/settings/github/check` calls the MCP server's `get_me` tool and returns `{ ok: true, login }` or `{ ok: false, error }`. It never returns the token.

## Rules

Do:

- Keep the client read-only with toolsets limited, and record the exact settings in the PR.
- Close every MCP client, and test that `close` runs on success, on error, and on abort.
- Treat tool output from GitHub as untrusted text. Issue bodies can contain instructions aimed at the model. Render it as text and links.

Avoid:

- Logging the token, the `Authorization` header, or a full request.
- Listing tools on every turn when the cache has them.

2. Read the github-mcp-server README and record the remote URL, the read-only setting, and the toolset setting in the PR comment.

Check that names get the `github_` prefix, that the read-only and toolset settings reach the server, that `close` runs on success, error, and abort, and that a second call within 5 minutes skips the list request. Also check that a wrong token gives a turn with no GitHub tools rather than an error.
4. Write `github.mjs`. Save the mock MCP URL and a fake token, press **Check**, and look for **Connected**. Send `[qa:github]` and check for a run card with issue links and an answer. Run the tests and the scenario. They must fail.

2. Implement `githubTools`, the cache, and the check route.

4. Run `npm test`, `npm run typecheck`, and `npm run build`.

### Turn 3. Prove it with verify-orbit

1. Run `launch --mock`, `doctor`, `browse github`, and `cleanup`.

3. Measure the time to first token for 10 turns with a token set and the cache warm, and for 10 turns with no token, alternating. Report both p50 values. The budget is at most 300 ms added at p50 when the cache is warm.
4. Post the output and the screenshots, update the changelog and the roadmap, and mark the PR ready.

## Done when

- `npm test`, `npm run typecheck`, and `npm run build` exit 0.
- **Check** shows the GitHub login for a valid token and the error for a wrong one.
- The model lists issues and reads a pull request through the MCP tools, and the card links to them.
- No write tool is available, and the PR records why.
- With a warm cache, GitHub tools add at most 300 ms at p50 to the time to first token.
