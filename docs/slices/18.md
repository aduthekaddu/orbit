# Slice 18. Accounts and hosting modes

Let several people use one Orbit install, each with their own account, chats, memories, and GitHub token. The admin picks one of three hosting modes for the install: `personal` (today's behavior), `team` (invited people share the admin's provider connections), or `community` (people bring their own keys). No one can read or change another person's data.

**Branches** 18a `feat/accounts`, 18b `feat/accounts-modes`. **Depends on** [slice 14](14.md) for `user_preferences` and [slice 17](17.md) for `provider_connections`. Slices 19 to 22 need only 18a. Slice 23 needs 18b, because its URL policy and its proof use `team` and `community` and it reuses `guardedFetch`. The decision is recorded in [ADR 0002](../adr/0002-several-users.md).

## Why

The maintainer confirmed on 14 November 2026 that one install should serve several people who create their own accounts. On keys, they asked for rules that fit who the install serves. That can be the host alone, other people, or the host's own team.

Opening signup on `main` today would leak one person's data to another. Chats, messages, and history search already filter by user. Memories, dreaming, settings, and the GitHub token do not. Any second account could list, edit, and delete every memory, overwrite the shared settings, and read the owner's private repositories through the owner's GitHub token. The full list, checked line by line against `291149c`, is in [Every unscoped read and write on main](#every-unscoped-read-and-write-on-main).

Open WebUI, LibreChat, LobeChat, and AnythingLLM all shipped advisories in 2026 for this class of bug, a missing owner check on one endpoint. Review alone did not catch them. This slice makes the owner check structural, then proves it with a test that walks every route.

### Two pull requests

The work is too large for one review, and the order matters for safety.

- **18a, foundation and data scoping.** Roles, the policy function, the settings split, per-user memory and GitHub, and the two route tests. The hosting mode is fixed to `personal`, so signup still closes after the first account. A scoping bug in 18a cannot leak data in production, because no second account can exist yet. Tests and the verify sandbox create the second account directly.
- **18b, modes, invites, and admin.** `team` and `community`, invite links, open signup, the users list and removal, connection sharing by mode, and the SSRF guard. It opens the door only after 18a's cross-user test is green on `main`.

Each part follows the three-turn workflow on its own branch.

## Scope

18a ships:

- `user.role` (`'admin' | 'member'`). The migration makes the existing account `admin`. At most one admin per install.
- One policy function, `policyFor(mode)` in `src/lib/policy.ts`, replacing the `user_single_row` trigger (`src/lib/db/index.ts:50-57`) and the hook in `src/lib/auth.ts:43-52`.
- `instance_settings` (one row) replacing `settings`. Admin-only routes under `/api/admin/`. An `/admin` page for search, the code sandbox switch, and the dream hour.
- A per-user GitHub token in `user_github`, encrypted at rest.
- Memories, memory runs, dreaming, embedding, and recall scoped by user. A per-user memory switch in `user_preferences`.
- The cross-user route test and the admin 403 test, both walking every route file.
- A schema ownership test that fails when a table holds user data without `user_id ... ON DELETE CASCADE`.

18b ships:

- `team` and `community` modes and the switching rules.
- Single-use invite links that expire, an `/invite/<token>` page, and open signup in `community`.
- Admin page sections for hosting mode, signup, invites, and users. Removing a user deletes all their data.
- Provider connection visibility and creation by mode, and a private-network guard on provider URLs in `community`.
- README, `ARCHITECTURE.md`, `SECURITY.md`, and roadmap changes that retire the one-user statements.

Does not ship:

- More than one admin, admin transfer, or demoting the admin.
- An admin view of anyone else's chats, memories, or keys. The ownership rule applies to the admin too.
- Email verification, password reset by email, single sign-on, or an approval queue.
- Per-member token budgets or model allowlists.
- Data export before removal.
- Checking the Cloudflare Access JWT inside Orbit (still on the roadmap's Later list).

## Design

### Data shape

```ts
type UserId = string & { readonly brand: "UserId" }; // only sessionFrom() and test fixtures make one
type Role = "admin" | "member";
type Viewer = { id: UserId; role: Role };

// 18a parses only "personal". 18b adds the other two, and every exhaustive switch must then handle them.
type HostingMode =
  | { kind: "personal" }
  | { kind: "team" }
  | { kind: "community"; signup: "invite" | "open" };

type InviteCheck = "none" | "valid" | "invalid";
type SignupDecision =
  | { ok: true; role: Role; invite: "consume" | "keep" }
  | { ok: false; reason: "closed" | "invite-required" | "invite-invalid" };

type Policy = {
  signup(input: { accounts: number; invite: InviteCheck }): SignupDecision;
  openWithoutInvite(accounts: number): boolean; // GET /api/setup and the /signup page
  mayInvite(viewer: Viewer): boolean;
  mayCreateConnection(viewer: Viewer): boolean;
  connectionOwner(viewer: Viewer, adminId: UserId): UserId; // whose connections the viewer may pick
  guardsPrivateHosts: boolean; // the SSRF check on provider base URLs
};

type InviteState =
  | { kind: "pending"; expiresAt: Date }
  | { kind: "claimed"; until: Date } // a signup is creating its account; pending again after `until`
  | { kind: "used" }
  | { kind: "expired" };
type ModeSwitch = { ok: true } | { ok: false; reason: "accounts-exist" };
```

`sandbox` is an admin switch on top of `ORBIT_SANDBOX=on`. The environment variable stays the hard gate, so the browser can never enable code runs the server did not allow. `tavily_key_ciphertext` uses the same AES-256-GCM helper slice 17 uses for provider keys, so every secret at rest is encrypted. The contract does not require this for the Tavily key. It costs one call while the column moves anyway.

`HostingMode` is stored in `hosting_mode` and, from 18b, `signup_mode`. `getInstance()` parses them into the union once. An unknown value throws at boot. 18a's parser accepts only `personal`.

### The policy function

`policyFor(mode)` in `src/lib/policy.ts` is a pure function with one exhaustive `switch`. It owns every rule that depends on the mode. Nothing else branches on `hosting_mode`.

| Rule | `personal` | `team` | `community` |
| --- | --- | --- | --- |
| Signup with 0 accounts | admin | admin | admin |
| Signup without invite | closed | invite-required | member if `open`, else invite-required |
| Signup with a valid invite | closed | member, consume | member, consume |
| `openWithoutInvite` | 0 accounts | 0 accounts | 0 accounts, or `open` |
| `mayInvite` | no | admin | admin |
| `mayCreateConnection` | admin | admin | everyone |
| `connectionOwner` | self | the admin | self |
| `guardsPrivateHosts` | no | no | yes |

`switchMode(from, to, accounts)` sits next to it. Any mode may switch to `team` or `community`. Switching to `personal` is refused while more than one account exists, and it deletes pending invites. Switching from `community` to `team` keeps members' connections and keys stored but unused, because `connectionOwner` now points at the admin.

### Signup

1. better-auth declares `user.additionalFields.role` with `input: false` and `defaultValue: "member"`. better-auth defaults `input` to `true` (`@better-auth/core/dist/db/type.d.mts:43-46`), which would let a signup body set `role: "admin"`.
2. `databaseHooks.user.create.before(user, ctx)` reads the invite token with `ctx?.getHeader("x-orbit-invite")`. The hook context is better-call's endpoint context, which has `getHeader` (`node_modules/better-call/dist/endpoint.d.mts:280-289`). A server-side call with no request gets `null`, which means no invite. In one synchronous `db.transaction` it counts users, looks the invite up by `token_hash = sha256(token)`, and asks `policyFor(mode).signup(...)`. On `consume` it claims the invite with `UPDATE invites SET claimed_at = :now WHERE id = ? AND used_at IS NULL AND (claimed_at IS NULL OR claimed_at < :now - 300000) AND expires_at > :now` and requires one changed row. The hook commits before better-auth inserts the user (`createWithHooks` in `node_modules/better-auth/dist/db/with-hooks.mjs` runs `before`, then the insert, then queues `after`), so it cannot spend the invite yet. If the insert then fails, for example on the email unique index, the claim lapses after 5 minutes and the link works again.
3. A refusal throws `APIError("FORBIDDEN", { message: "Signup is closed" })`, the same as `auth.ts:48` today. Success returns `{ data: { ...user, role } }`.
4. `after(user, ctx)` reads the same header again and spends the invite with `UPDATE invites SET used_at = :now, used_by = :userId WHERE token_hash = ? AND used_at IS NULL`. `used_at` never goes back to null, so removing that member later does not reopen the link, even though `used_by` becomes null. For the first admin it seeds `user_github` from `ORBIT_GITHUB_TOKEN` when set.
5. The partial unique index closes the first-account race. Two parallel first signups both decide `admin`, and the second insert fails. Open WebUI had this race (GHSA-h3ww-q6xx-w7x3).
6. `GET /api/setup` keeps its shape, `{ signupOpen: boolean }`, from `openWithoutInvite`. The verify harness, `scripts/qa/assert-nonroot.sh`, and the smoke scripts read it.

Prior art. better-auth's admin plugin was considered and rejected. It adds impersonation and set-password endpoints under `/api/auth/admin/*`, which would let an admin read a member's chats. A single `additionalFields` column is enough.

### Memory per user

Every helper in `src/lib/memory/store.ts` takes `userId: UserId` first and filters on `memories.user_id`: `getMemory`, `listMemories`, `saveMemory`, `updateMemory`, `deleteMemory`, `memoryCount`, `listUnembedded`, `textMatchIds`, `vectorMatchIds`, `markUsed`. `writeVectors` reads `user_id` from the memory row it embeds and writes it as the partition key. It never takes the partition from a caller. The `memorySelect` join on chats (`store.ts:54`) adds `AND chats.user_id = memories.user_id`.

- **Recall.** `recall(userId, query, k)`. The vector query becomes `WHERE embedding MATCH ? AND k = ? AND user_id = ?`, so the 20 nearest are the user's 20 nearest. A filter after the KNN would starve a user whose neighbors belong to someone else.
- **Embedding.** `embedPending(userId)` and `memoryEmbeddings(userId)` fill only that user's rows. The global `chain` that serializes Ollama calls stays.
- **Dreaming.** `runDream({ userId, ... })`. Every `memory_runs` statement filters on `user_id`, and `CLAIM_SQL` conflicts on `(user_id, date)`. `changedChatIds` joins `chats` on `chats.user_id = ?`. `nearest` joins `memories` on `memories.user_id = ?`. The provider comes from that user's pickable connection, so in `community` each person's dream spends their own key. A user with no pickable connection fails their own run with `No provider is saved` and nobody else's.
- **Scheduler.** Each tick in `startDreamScheduler` lists users with memory on whose run for tonight is missing or has a stale lease, then runs them one after another. An in-process flag stops a second tick from starting while a pass runs. The lease still guards other processes.
- **Memory off.** No recall notes, no `remember` or `forget` tools, no dreaming. `/memory` still lists and deletes existing memories.
- **CLI.** `npm run dream -- [--date YYYY-MM-DD] [--user <email>]`. No `--user` dreams for every user with memory on. The email lookup is an exact `=`.

### Provider connections by mode

One function, `pickableConnection(viewer, requested)`, resolves the connection for a chat turn, a title, a dream, and the model list. A connection is pickable when its `user_id` equals `policy.connectionOwner(viewer, adminId)`. `requested` is `{ from: "request"; id } | { from: "stored"; id } | null`, so the two cases cannot mix:

- **From a request.** An id the person just sent, in the chat body's `modelChoice` or in `PUT /api/preferences/model`, that is not pickable answers 404. That is slice 17's rule for `resolveChoice`, and it stays.
- **From storage.** An id read from `chats.connection_id` or `default_connection_id` that is no longer pickable is not an error. A mode change made it stale. It falls back to the viewer's `default_connection_id`, then to the first pickable connection, then to none, which the chat route answers with its existing 400.

It runs on every use, not only when `chats.connection_id` or `default_connection_id` is written, because the mode can change after the write.

Members see `{ id, label, kind }` for a connection they do not own. Base URL and key flags go only to the owner. Create, update, and delete check `mayCreateConnection`, then ownership (404).

18b adds `guardedFetch(blocked)` in `src/lib/net-guard.ts` for `community`. `blocked` is a `net.BlockList`, which is built into Node. `PUBLIC_BLOCKLIST` holds `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`, `::/128`, `::1/128`, `fc00::/7`, `fe80::/10`, `ff00::/8`, and the IPv4-mapped IPv6 forms of the IPv4 ranges. `guardedFetch` is `fetch` from `undici` with a `dispatcher` of `new Agent({ connect })`, where `connect` is a function that checks the host of every new socket and then calls undici's `buildConnector`:

- An IP literal (`net.isIP` after stripping IPv6 brackets) is checked directly. Node and undici skip `lookup` for an IP literal. On 14 November 2026, with undici 7.30.1, an `Agent` whose `connect.lookup` refused every host still fetched `http://127.0.0.1:<port>/`, and the lookup was never called. A guard in `connect.lookup` alone would let `http://10.0.0.1/v1` and a redirect to `http://127.0.0.1/` through.
- A name goes to `buildConnector({ lookup })`. That `lookup` resolves with `dns.lookup(host, { all: true })` and fails when any address is blocked. The socket uses the address that was checked, so a DNS answer that changes between save and connect cannot slip through (LibreChat GHSA-gc9r-88c3-7qhq).

undici's `fetch` follows a redirect through the same dispatcher, so every hop opens its socket through this check. In the same check on 14 November, a `connect` function in this shape saw both hosts when a server on `127.0.0.1` redirected to `127.0.0.2`, and refusing the second host stopped the request. Add `undici` as a direct dependency at `7.30.1`, the version already in the lockfile. Slice 23 reuses `guardedFetch` for MCP servers. The AI SDK provider factories take a `fetch` option, so the guard wraps model calls and model listing. Saving a connection in `community` also resolves the host once and refuses a private address with `Use a public URL.` `ORBIT_PROVIDER_FIXTURE=1` allows loopback only, for the verify harness, the same way `ORBIT_GITHUB_MCP_FIXTURE` does (`src/lib/tools/github.ts:53`).

Invites expire after 7 days. The token is 32 random bytes in base64url. Only its SHA-256 is stored. The link is `<auth base URL>/invite/<token>`, from `resolveAuthBaseUrl` in `src/lib/auth-origins.ts:9`. Nothing hardcodes an origin.

Removing a user is `DELETE FROM user WHERE id = ? AND role = 'member'`. Cascades remove sessions, accounts, chats, messages, memories, memory runs, `user_github`, `user_preferences`, and the user's own connections. FTS triggers clean the search indexes, and `memories_vec_ad` cleans the vectors. A cascade fires that trigger (checked on an in-memory sqlite-vec 0.1.9 database). An open stream for that user finds its chat gone, and `upsertMessage` returns false (`src/lib/messages.ts:135-136`). A running dream loses its lease row and stops.

Layout. `/admin` uses the `/settings` shell and column width. At 360 and 390px every section is one column. Each row keeps its action on the right, and the email truncates first. The sidebar shows an **Admin** link after Settings (`src/components/chat/sidebar.tsx:128-140`), the palette adds **Admin** after Memory (`src/components/shell/command-palette.tsx:116-119`), and `app-shell.tsx:107` titles the page. All three appear for the admin only.

### Boundaries

- **Session.** `sessionFrom(request)` in `src/lib/session.ts` replaces `getSession()` in every route handler. It reads the session from the request's headers instead of `next/headers`, so a test can call a handler in-process, and it parses `role` with zod into `{ id: UserId; email; role }`. Pages keep `requireUser()` and add `requireAdminPage()`. With `session.cookieCache` off, as today, better-auth should load the user row with each session lookup, so a removed user loses access at once. That is inferred from better-auth's defaults, so the cross-user test checks that a removed member's cookie gets 401. Leave `cookieCache` off.
- **Instance row.** `getInstance()` parses the row into `HostingMode` and the rest. Code behind it trusts the type.
- **Proxy.** 18b adds `/invite/` as a public prefix in `src/proxy.ts`. A signed-in visitor there goes to `/`, as on `/login`. No other public path changes. The matcher (`proxy.ts:34`) is untouched, and no new URL ends in an image extension.
- **Identity lookups.** Email and token-hash lookups use `=`. Never `LIKE` (Open WebUI GHSA-wpmr-8h3q-fwj7).
- **Cloudflare Access.** Access stays optional, and the maintainer has not decided. No path in this slice needs a bypass rule. A bypass on `/invite/*` would let a stranger create an account and then hit Access on every other page, so it buys nothing. The README text is in 18b's Files list.
