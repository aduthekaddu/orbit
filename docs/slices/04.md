# Slice 4: Branching

Make edit and regenerate keep the old version. A chat becomes a tree. Arrows under a message (`‹ 2 / 3 ›`) switch between its versions, and a reload shows the branch you were last on.

**Branch** `feat/branching`. **Depends on** [slice 3](03.md) for the browse drive. **Refs** #11 items 3 and 4.

## Why

Today an edit deletes every message after the edited one, and a regenerate overwrites the reply. Users of ChatGPT and Claude expect to try another wording and then go back to the first answer. Losing an answer you liked is the worst outcome a chat app can have, and Orbit causes it on purpose today.

## Scope

Ships:

- An edit adds a new user message beside the old one. Both keep their replies.
- A regenerate adds a new reply beside the old one.
- The branch picker under any message that has siblings.
- A reload opens the branch that was written last.

Does not ship:

- Remembering a branch you switched to without sending. A reload opens the last written branch.
- Deleting a branch.
- A tree view of the whole chat.

## Design

### Data shape

The thread is a tree of messages. Each message points at its parent. The chat points at the leaf of the active branch.

```ts
type StoredMessage = {
	id: string;
	chatId: string;
	parentId: string | null; // null only for the first message of the chat
	role: "user" | "assistant";
	parts: UIMessage["parts"];
	createdAt: Date;
};

type Chat = {
	id: string;
	headId: string | null; // leaf of the last written branch
};
```

assistant-ui already models the same tree. `ThreadHistoryAdapter.load()` in `@assistant-ui/core` returns `{ headId, messages: { parentId, message }[] }`. `useChatRuntime` from `@assistant-ui/react-ai-sdk` 1.4.21 accepts it as `adapters.history`. The browser keeps the tree, and the branch picker reads it.

### Schema change

One Drizzle migration:

- `messages.parent_id`, a nullable text column with an index on `(chat_id, parent_id)`.
- `chats.head_id`, a nullable text column.
- A backfill. For each chat, set every message's `parent_id` to the message before it by `position`, and set `head_id` to the last message.

`position` stays. It becomes the depth in the tree, which the thread map and the ordering of siblings by `created_at` still use. Drop no column in this slice.

### Who writes what

The server still owns history. `/api/chat` stays the only writer of new messages.

- `planChatWrite` stops deleting rows on an edit. It checks that the incoming messages form one path from the root. Each incoming message's parent is the one before it. A path that does not exist in the tree is stale and gets `409`.
- An edited user message is a new row whose parent is the edited message's parent.
- A regenerate reply is a new row whose parent is the user message. `responseIdFor` returns a new id for a regenerate instead of reusing the old answer's id.
- When the user message is saved, the route sets `chats.head_id` to that user message. When the reply is saved, it sets `chats.head_id` to the reply. A provider failure and a stop before visible text both leave the head on the user message, so a reload shows that prompt.
- The history adapter's `load()` reads the tree from the page props. Its `append()` does nothing, because `/api/chat` already stored the message. Write a comment that says so, since it reads like a bug otherwise.

`GET /api/chats/:id` returns `{ headId, messages: { parentId, message }[] }` instead of a flat list.

### The stop rule still holds

The rule from slice 3 becomes simpler. A stopped regenerate makes a new sibling, so it can never overwrite the old reply. `shouldSaveReply` keeps protecting against empty replies. Keep the existing turn rules from [ARCHITECTURE.md](../../ARCHITECTURE.md#the-rules-of-a-turn) true and update the model in `docs/architecture/ChatTurn.tla` if a rule changes meaning.

## Rules

Do:

- Put tree logic in `src/lib/chat-tree.ts` as pure functions over arrays, and test them there.
- Keep the stale-write `409` for any incoming path that the tree does not contain.
- Write the migration so it is safe to run twice. A second run changes nothing.

Avoid:

- Writing messages from the history adapter. Two writers make two copies of each message.
- Changing message ids that the client sent. If assistant-ui sends the edited message under the old id, record that in turn 1 and mint the new id in the transport, not on the server.

## Done when

- `npm test`, `npm run typecheck`, and `npm run build` exit 0.
- Regenerate and edit both keep the old version, and the picker switches between versions.
- A reload shows the last written branch with its pickers.
- A stale tab still gets `409` and loses nothing.
- The migration runs on an existing database, and a second run changes nothing.
